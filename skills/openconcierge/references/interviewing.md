# Interviewing — Eliciting Real Needs

The interview exists to make search and ranking accurate, not to fill out
a form. Every question you ask should have an answer that can change
eligibility, ranking, budget, region, safety, or product type. If it
can't, don't ask it.

## How to interview

- **Conversational, not interrogative.** Ask in natural language, at most
  2-3 questions per message. Batch related questions rather than firing
  them one at a time.
- **Anchor on the problem.** "The one I'm using hurts my neck and I sleep
  hot" is worth more than any spec sheet. Probe the problem before
  probing features.
- **Work from the brief.** After each answer, update the shopping brief.
  Ask only about fields still missing that matter for this category.
- **Category judgment.** What is decision-relevant differs per category:
  - *Pillow:* sleep position, firmness, materials, allergies, budget.
  - *Laptop:* primary use, OS preference, portability, battery, budget.
  - *Gift:* recipient, relationship, interests, occasion, budget range,
    what they already have.
  Don't recite this list — let the user's problem statement tell you
  which gaps matter.

## Questions that change decisions

Ask about, in rough priority order:

1. **Budget** — a maximum, and currency if ambiguous. Changes eligibility
   (hard filter) more than anything else.
2. **Region** — where it must ship/deliver. Changes availability.
3. **Deadline** — needed-by date. Changes fulfillment options and filters.
4. **Must-haves** — features that are non-negotiable (hard filter).
5. **Problem specifics** — the details that separate "firm support" from
   "gel-infusted memory foam" (i.e., what to actually search for).
6. **Avoid list** — brands, materials, retailers to exclude.
7. **Intended user** — for whom; sizing and safety-relevant context
   (allergies, children, disability needs) if volunteered.

The user may decline to answer any of these. That's fine.

## When to stop

**Stop asking once a useful search is possible.** A useful search is
possible when you can construct search queries that will surface
candidates likely to satisfy the brief — typically: category known,
problem known, budget known or explicitly open, region known or assumed
from conversation language, and no obviously-missing safety-relevant
fact. You do not need a complete brief to search. Search results
themselves will reveal what else to ask about.

If you're unsure whether to ask one more question, ask yourself: "could
this answer change which products are eligible, or how I rank them?" If
no — search now.

## "Use your judgment"

If the user says "use your judgment" (or "you pick", "whatever you think
is best", or just seems impatient with questions):

1. Stop interviewing immediately.
2. Fill remaining gaps with sensible defaults appropriate to the problem.
3. **Say which defaults you chose**, in one or two lines, so the user can
   correct them cheaply. E.g. "I'll assume under $80, queen size, and
   prioritize neck support and cooling."
4. Proceed to research. Do not ask permission to proceed.

## Mid-task revisions

The user may revise the brief at any time — "actually my budget is $50",
"no memory foam", "wait, it's for my wife".

- Fold the revision into the brief.
- Re-derive what actually changed: a new budget may eliminate or admit
  candidates; a new material constraint may invalidate evidence.
- Re-research only what the revision touches. Don't discard good evidence
  for unchanged requirements.
- If previously-presented options are invalidated, say so explicitly and
  re-rank.

## Memory first

Before asking anything, check memory the host exposes. If a stable
preference (region, currency, budget sensitivity, preferred/avoided
brands, sizing, health context) is already recorded, use it silently and
confirm it only if it conflicts with what the user just said. Never ask
for what you already know.
